# Режим VPN-шлюза на двух VPS

Телефон подключается к AmneziaWG на первом VPS. APM на этом VPS применяет политику к пакету по IP назначения. Пакет выходит в интернет с первого VPS, проходит по исходящему AmneziaWG-туннелю ко второму VPS или блокируется. Страна второго VPS задаётся выбором endpoint независимо от списка назначений.

## Зачем нужен региональный вход

Мобильный оператор видит соединение телефона с публичным IP первого VPS. Второй туннель начинается на первом VPS. Сервер приложения видит публичный IP того VPS, через который его трафик вышел в интернет. Если первый VPS также обслуживает `direct` с того же IP, сервер приложения видит этот же адрес. Блокировка входного IP, сбой связи между VPS и отказ сервиса по IP выхода проверяются отдельно.

На личном iPhone используется обычный VPN-профиль AmneziaWG. Штатный Per-App VPN требует, чтобы приложением управляла система управления устройствами (MDM). Шлюз выбирает маршрут по назначению, поэтому запросы одного приложения к разным адресам могут пойти через разные выходы. На самом телефоне VPN остаётся активен. iOS также исключает из туннеля некоторые системные соединения. Правила шлюза применяются к принятым им пакетам. [Per-App VPN в руководстве Apple](https://support.apple.com/en-kw/guide/deployment/depae3d361d0/web) · [Исключения VPN в iOS](https://developer.apple.com/documentation/networkextension/nevpnprotocol/includeallnetworks)

## Поведение

| Политика | Адрес из списка | Адрес вне списка |
|---|---|---|
| Блокировать адреса РФ | `block` | `tunnel` |
| Адреса РФ через первый VPS | `direct` | `tunnel` |
| Только адреса РФ через второй VPS | `tunnel` | `direct` |
| Доступ только к адресам РФ через второй VPS | `tunnel` | `block` |

Оба действия выбираются независимо. `direct` означает выход с публичного IP первого VPS. `tunnel` означает выход с публичного IP второго VPS. При потере второго туннеля `tunnel` блокируется, а `direct` сохраняет доступ через первый VPS. Штатный `apm stop` закрывает транзит полностью.

Первая версия рассчитана на Linux, один входящий AmneziaWG-интерфейс в сетевом пространстве хоста и один исходящий туннель. Входящий VPN и выход в интернет на втором VPS настраивает администратор. Первая версия маршрутизирует IPv4. Профиль телефона забирает и IPv4, и IPv6, а шлюз блокирует транзитный IPv6. Поддержка входящего VPN в Docker, маршрутизация IPv6 и правила по доменам требуют отдельных этапов.

## 1. Проверить схему вручную

1. Поднять входящий AmneziaWG на первом VPS и назначить отдельную подсеть телефона. На втором VPS подготовить AmneziaWG peer для первого VPS, IPv4 forwarding и NAT к публичному интерфейсу. Подсети двух туннелей должны различаться.
2. Проверить выбор выхода через `nftables` и отдельную таблицу маршрутов. Применять политику к пакетам с внутреннего VPN-интерфейса. Проверить прямой доступ к SSH и маршрут публичного UDP endpoint второго VPS во всех сценариях. [ip-rule(8)](https://man7.org/linux/man-pages/man8/ip-rule.8.html) · [Документация nftables](https://netfilter.org/projects/nftables/manpage.html)
3. Проверить на телефоне четыре политики из таблицы и обрыв второго туннеля. Для проверки фиксировать фактический IP на стороне внешних сервисов, проверять TCP, UDP и DNS. Проверить рабочий MTU на обоих участках и прохождение ответов через исходящий AWG при настройках `rp_filter` выбранного VPS.
4. С личного iPhone проверить подключение на мобильной сети целевого региона и по Wi-Fi. Сравнить прямое подключение к выходному VPS с подключением через региональный вход на той же сети. Зафиксировать доступность каждого входного адреса, задержку, скорость и потери под нагрузкой. Проверить выбранные приложения с российским и зарубежным выходом. Отказ приложения при работающем туннеле фиксировать отдельно от блокировки VPN endpoint.

Результат этапа — воспроизводимые настройки двух VPS и подтверждённые маршруты. После этого перенести политику в APM.

## 2. Добавить конфигурацию шлюза

Предлагаемый фрагмент для политики «адреса списка блокировать, остальное через второй VPS».

```ini
GATEWAY_ON=on
GATEWAY_INGRESS_IF=awg-in
GATEWAY_WAN_IF=eth0
GATEWAY_CIDRS=203.0.113.0/24
GATEWAY_MATCH_ACTION=block
GATEWAY_DEFAULT_ACTION=tunnel
VPN_ON=on
PROXY_ON=off
```

`203.0.113.0/24` — демонстрационный префикс. Для реальной политики администратор задаёт IPv4/CIDR вручную или через HTTPS в `GATEWAY_CIDR_URLS`. Для разных действий нужен непустой список. Некорректный или пустой ответ заданного URL отменяет активацию. Переиспользовать загрузку и точное объединение CIDR из [сетевого модуля](../../lib/network.sh), сохранив текущую обработку `IPLIST_URLS` в клиентском режиме.

Если одно из действий — `tunnel`, требовать `VPN_ON=on` и существующие параметры исходящего VPN. Для сочетаний `direct` и `block` разрешить `VPN_ON=off`. В режиме шлюза требовать `PROXY_ON=off`, а непустые `ALLOWED_IPS`, `IPLIST_URLS` и `DNS` отклонять с подсказкой: маршруты для телефона задаются политикой шлюза, DNS-сервер — профилем телефона. `config validate` проверяет синтаксис и сочетания параметров офлайн. `doctor` проверяет зависимости, интерфейсы, forwarding и наличие базовой защиты без изменения сети.

## 3. Реализовать маршрутизацию и защиту

- **Исходящий туннель.** Переиспользовать AWG-конфиг, владение интерфейсом и проверку handshake. В режиме шлюза генерировать `AllowedIPs = 0.0.0.0/0` для исходящего peer и `Table = off`. Выделенная таблица APM применяется по метке и входящему интерфейсу. Остальной трафик хоста использует его штатные маршруты. Проверку endpoint перевести на фактически используемый маршрут в этом режиме. [Текущий код туннеля](../../lib/tunnel.sh) · [Описание Table в awg-quick](https://github.com/amnezia-vpn/amneziawg-tools/blob/master/src/man/wg-quick.8)
- **Политика пакета.** Хранить CIDR в интервальном наборе `nftables`. На входе классифицировать IPv4 по адресу назначения, отбрасывать `block` и маркировать `tunnel` для отдельной таблицы. В `FORWARD` пропускать `tunnel` только через текущий исходящий AWG-интерфейс, `direct` только через заданный WAN, обратно — ответы на разрешённые соединения. Добавить завершающее правило `unreachable` для помеченного трафика, если в таблице исчез маршрут. Проверка действий должна применяться и к уже открытым исходящим потокам. [ip-rule(8)](https://man7.org/linux/man-pages/man8/ip-rule.8.html) · [Документация nftables](https://netfilter.org/projects/nftables/manpage.html)
- **NAT и доступ к VPS.** Ограничить masquerade клиентским транзитом на разрешённых выходах. При выходе в туннель первый VPS подменяет источник на свой адрес в этом туннеле, второй делает NAT в интернет. Закрыть для VPN-клиентов доступ к управлению первым и вторым VPS и к облачным metadata endpoints. Администратор настраивает IPv4 forwarding на VPS при развёртывании.
- **Базовая защита.** Настройка первого VPS устанавливает постоянную таблицу `nftables`, которая закрывает транзит через входящий VPN с момента загрузки. APM атомарно активирует правила в этой таблице после подготовки маршрутов и успешного handshake, когда политике нужен туннель. На `stop` и при ошибке запуска сначала вернуть блокирующие правила, затем убрать собственные маршруты и туннель. При `SIGKILL` действующие правила должны по-прежнему запрещать выход `tunnel` через WAN. При смене интерфейса держать прежний вход закрытым, пока администратор его не отключит.

## 4. Встроить в запуск и диагностику

- Подключить шлюз к `start`, `stop` и `restart`. Сохранять параметры и принадлежность активных ресурсов в [состоянии сессии](../../lib/session.sh), чтобы `stop` работал после изменения файла конфигурации. Сериализовать активацию одной политики на хост. При занятой метке, таблице или уже активной сессии отклонять новый запуск до изменения сетевых правил.
- Обновлять список и политику через штатный `restart`. На время переключения транзит закрыт. Проверенный набор CIDR и соответствующие правила публикуются одной операцией `nftables`. Соединения, для которых меняется выход, могут потребовать повторного подключения из-за существующих записей NAT.
- В `status` показать выбранные действия, интерфейсы и состояние транзита. В `diagnose` проверить применённые правила, счётчики, маршруты для VPN-клиентов и состояние туннеля. Handshake подтверждает связь с peer. Сквозную доступность интернета проверять отдельным запросом через шлюз.
- Обновить шаблон конфига, справку и документацию установки. Добавить пример запуска под `systemd` с загрузкой блокирующих правил до включения входящего VPN. Описать профиль телефона с полным туннелем для обеих IP-версий и IPv4 DNS-резолвером, доступным по выбранной политике. Указать, что трафик DNS и DoH оценивается по IP резолвера. Названия доменов и страна владельца сервиса могут расходиться с геолокацией IP. [Ограничения GeoIP](https://dev.maxmind.com/geoip/docs/databases/city-and-country/)

## 5. Приёмка

| Проверка | Ожидаемый результат |
|---|---|
| Все сочетания `match` и `default` | Для адреса из списка и вне списка наблюдается заданный выход или блокировка |
| Падение peer, удаление AWG-интерфейса или его маршрута | На WAN виден только разрешённый `direct`, пакеты `tunnel` туда не выходят |
| `stop`, `SIGKILL`, частичный запуск, перезагрузка VPS | Транзит закрыт или продолжает работать по последней применённой политике без обхода туннеля. После штатного `stop` и до активации он закрыт |
| Ошибка или пустой ответ источника CIDR | Политика не активируется, транзит закрыт |
| Внешние IP при подключении с iPhone | VPN на телефоне подключается к первому VPS. Контрольный сервис видит IP первого VPS для `direct` и IP второго для `tunnel` |
| TCP, UDP, DNS и IPv6 с телефона в двухстековой сети | IPv4 следует политике, DNS работает по выбранному пути, IPv6 не обходит шлюз |
| SSH и сторонний трафик хоста | Сохраняют маршруты во время запуска, обрыва и остановки APM |
| Старые конфиги и режимы APM | Проходят текущие тесты VPN-only, proxy-only и совместного режима |

Основные проверки маршрутизации и утечек выполнить в изолированных Linux network namespaces с узлами «телефон», «первый VPS», «второй VPS» и контрольным назначением. Проверять пакеты на обоих выходах, включая длительное соединение при переходе политики. Перед релизом повторить сквозную проверку с телефоном на двух реальных VPS, снять фактические IP выхода и проверить загрузку после перезагрузки.
