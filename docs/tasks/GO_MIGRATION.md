# Задача: переход CLI с Bash на Go

Статус: запланировано, реализация не начата. Дата обсуждения: 2026-10-02.

## Цель

Перенести менеджер на Go, сохранив пользовательские команды, конфигурацию и
гарантии безопасности Linux-версии. Создать общее ядро для последующей поддержки
Linux, macOS и Windows с отдельными реализациями системных операций.

Первая законченная поставка — Go CLI для Linux с подтверждённым соответствием
текущему поведению. Нативная поддержка macOS и Windows — отдельные этапы;
сборка бинарника для ОС сама по себе не означает поддержку её сетевого стека.

## Границы

- AWG и 3proxy остаются внешними компонентами; собственные VPN-протокол и
  прокси-сервер в рамках задачи не реализуются.
- Сохраняются start/stop/restart/status/diagnose/test/logs, config validate,
  --config, --help и --version.
- Сохраняются формат KEY=value, действующие параметры и defaults, включая
  ALLOWED_IPS, IPLIST_URLS и BLOCK_IPV6; конфиг не исполняется как shell-код.
- Сохраняются пользовательские XDG-пути и AMNEZIA_PROXY_* на Linux,
  fallback старого конфига и привычное имя команды.
- Изменения модели привилегий, TTL-кэш, новые поля upstream, GUI и установочные
  пакеты рассматриваются отдельно, чтобы не смешивать их с переносом.

## Предлагаемая архитектура

Общее ядро отвечает за CLI, конфигурацию, валидацию, IP-списки, генерацию
конфигов, healthcheck, логи и последовательность операций. Платформенный слой
отвечает за туннели, маршруты, firewall, DNS, идентификацию процессов/интерфейсов,
блокировки и защищённое хранение runtime-состояния.

Интерфейсы определяются по реально нужным операциям, а не копируют каждый
Bash-вызов. Для ОС используются отдельные файлы/пакеты с ограничениями сборки.
Linux-реализация сначала может вызывать существующие awg-quick, ip и nft через
явные аргументы процесса. Произвольное выполнение shell-строк не допускается.

На первом этапе сохраняется текущая необходимость sudo для Linux-сетевых
операций. Архитектура должна позволять позже вынести их в отдельный helper или
службу. Windows-права и управление службами определяются в Windows-этапе.

## Этапы

1. Зафиксировать контракт совместимости.
   Описать команды, exit codes, defaults, формат конфига и состояние на диске.
   Составить сценарии сравнения Bash/Go, включая негативные и аварийные случаи.
2. Подготовить каркас и проверки Go.
   Добавить Go module, CLI и минимальные платформенные интерфейсы. Выбрать
   версию Go и зависимости; встроить gofmt, go vet и go test в CI.
3. Перенести общее поведение без изменения сети.
   Конфиг и validate, IPv4/CIDR, ручные/HTTPS-списки, генерация AWG/3proxy,
   логи и HTTP/SOCKS-healthcheck. Проверить пароли с двоеточием, кавычки,
   недоступные источники и отсутствие секретов в выводе.
4. Реализовать Linux-жизненный цикл.
   Lock, ownership, запуск/остановка, rollback, сигналы, таймауты и диагностика.
   Сохранить nftables-защиту, IPv6-блокировку и fwmark-проверку полного VPN.
5. Проверить совместимость и переход между версиями.
   Выполнить изолированные kernel-тесты и испытания настоящего AWG/3proxy.
   Описать обновление и откат, затем переключить основной launcher на Go.
6. Подготовить платформенные расширения.
   Проверить сборку общего ядра для macOS/Windows, добавить контрактные тесты.
   Нативную сеть и защиту реализовывать и принимать отдельными задачами.

## Требования к безопасности и состоянию

- Секретные файлы создаются сразу с ограниченным доступом; проверяются владельцы,
  права, симлинки и принадлежность ресурсов до привилегированных операций.
- Lock и идентификация процесса защищают от параллельного запуска и повторного PID.
- Данные для восстановления сохраняются до установки сетевой защиты.
- Ошибка обязательной защиты запрещает запуск. Ошибка очистки сохраняет
  состояние и защиту для повторного stop; IPv6 снимается последним.
- Отмена операции и SIGINT/SIGTERM приводят к контролируемой очистке;
  после SIGKILL восстановление работает по сохранённому состоянию.
- stop не требует исправного исходного конфига; чужие ресурсы не захватываются.
- Формат runtime-состояния версионируется. Выбрать и документировать одно из
  решений: безопасная совместимость с Bash-записями либо обязательный stop
  старой версией до обновления. Несовместимое состояние не удаляется молча.

## Критерии готовности Linux-переноса

- Пользователь может использовать прежний конфиг и основные команды Go CLI.
- Коды диагностики 0/1/2/3 и отсутствие ложного OK подтверждены тестами.
- Ручные и удалённые списки, их объединение и полный IPv4 работают как прежде;
  ошибка источника не расширяет маршруты и не повреждает последний сохранённый список.
- Сетевые испытания подтверждают блокировку upstream вне VPN, IPv6 вне loopback
  и корректный путь endpoint при полном VPN.
- Пройдены сценарии частичного запуска, TERM, зависшего процесса, SIGKILL,
  повторного stop и подмены интерфейса/PID; чужие ресурсы сохранены.
- Проверены корректное сохранение секретов, права файлов и отсутствие утечек в логах.
- CI выполняет проверки Go и интеграционные тесты; Bash остаётся эталоном до
  подтверждения соответствия. Race detector применяется к поддерживаемым
  тестам общего ядра и жизненного цикла.
- Описаны установка бинарника, зависимости, обновление и откат.

## Связанные задачи и открытые решения

- [Поддержка macOS](MACOS.md): реализовать платформенный слой на общем Go-ядре;
  предварительные испытания AWG на Mac можно провести до завершения переноса.
- Windows: исследовать управление AWG-службой, маршруты/DNS, ACL и защиту через
  Windows Firewall/WFP; нативные испытания обязательны перед заявлением поддержки.
- Определить минимальную версию Go, необходимость сторонней CLI-библиотеки,
  схему runtime-состояния и способ передачи SOCKS-запросов для healthcheck.
- Решить, какие существующие тесты станут проверками CLI, а какие нужно
  перенести с source Bash-функций на Go API. Простая замена команды запуска
  не переносит весь текущий тестовый набор.
