# Задача: устанавливаемая Linux-утилита

Статус: запланировано, реализация не начата. Дата: 2026-10-31.

## Цель и первая поставка

Пользователь устанавливает программу, создаёт конфиг и запускает команды из
любого каталога без зависимости от исходного Git-репозитория. Первая поставка
использует текущие Bash/Python-компоненты и поддерживает Linux.

В поставку входят установка, удаление, начальная настройка, проверка
зависимостей, правила обновления и тестирование установленной копии.
Существующие команды, коды завершения, XDG-пути, AMNEZIA_PROXY_* и fallback
на `~/.amnezia-proxy.conf` сохраняются. `start` продолжает работать в foreground;
sudo используется для существующих сетевых операций.

Go, macOS/Windows, systemd, .deb/.rpm, автоматическая установка зависимостей,
автообновление и shell completion — последующие задачи.

## 1. Зафиксировать установочный контракт

Определить интерфейс Makefile:

```bash
# Планируемые команды; сейчас ещё не реализованы.
make install PREFIX="$HOME/.local"
sudo make install PREFIX=/usr/local
make uninstall PREFIX="$HOME/.local"
make install PREFIX=/usr DESTDIR=/tmp/amnezia-package
```

По умолчанию `PREFIX=$HOME/.local`. Системный prefix задаётся явно.
Предусмотреть `BINDIR`, `LIBEXECDIR` и `DATADIR` с defaults от PREFIX;
все конечные каталоги — абсолютные. DESTDIR используется только как корень
сборочной раскладки и не попадает в пути внутри установленной программы.

Предлагаемая раскладка:

```text
$PREFIX/bin/amnezia-proxy-manager             публичный launcher
$PREFIX/bin/amnezia-proxy-gui                 публичный GUI launcher
$PREFIX/libexec/amnezia-proxy-manager/
    amnezia-proxy-manager                    внутренний launcher
    bin/amnezia-proxy                        основной CLI
    bin/amnezia-proxy-gui                    Chromium/Electron launcher
    lib/*.sh                                библиотеки
    lib/*.py                                вспомогательные программы
$PREFIX/share/amnezia-proxy-manager/
    config.example                          шаблон без пользовательских секретов
$PREFIX/share/doc/amnezia-proxy-manager/
    README.md
    REFERENCE.md
```

Публичные launcher'ы должны адресовать установленное дерево явно. Внутри
дерева сохраняются существующие относительные связи CLI и библиотек.
Фактический путь приложения фиксируется при запуске; смена cwd не меняет его.

**Готово, когда:** раскладка, имена команд и переменные описаны в справочнике;
учтены раздельные PREFIX и DESTDIR, а также пути с пробелами. Ориентиры:
[каталоги GNU](https://www.gnu.org/prep/standards/html_node/Directory-Variables.html)
и [DESTDIR](https://www.gnu.org/prep/standards/html_node/DESTDIR.html).

## 2. Подготовить запуск из установленного дерева

- Проверить вычисление PROJECT_ROOT в корневом launcher, обоих CLI и вызовах
  Python. Установленный публичный wrapper запускает внутренний entrypoint;
  запуск непосредственно из checkout также сохраняется.
- Ввести единый способ поиска `config.example` для checkout и установки.
  Не добавлять отдельный парсер пользовательского конфига в launcher.
- Проверить пути к `vpn_link.py`, `collapse_routes.py`, проверкам firewall и
  `sandbox_forwarder.py`, включая проверку cmdline при остановке forwarder.
- Сохранить cwd вызывающего пользователя для `run`, HOME/PATH и GUI env,
  активный proxy endpoint и маскирование секретных runtime-файлов.

**Готово, когда:** копия в подготовленной раскладке выполняет `--help`,
`--version`, `config validate` и Python-операции при недоступном checkout;
`run` получает исходный cwd. Проверки не обращаются к библиотекам из репозитория.

## 3. Добавить Makefile: install и uninstall

- Устанавливать только явный список программных файлов, шаблон и документацию.
  Git, тесты, отчёты аудита, реальные конфиги и runtime в поставку не входят.
- Задать права: исполняемые entrypoint'ы 755, библиотеки/документация 644,
  каталоги 755. Системные файлы принадлежат пользователю установки/root;
  программа при запуске не меняет их права и не требует записи в libexec.
- Проверять корректность назначения до копирования; сначала подготавливать
  файлы во временном каталоге. Ошибка установки должна сохранять предыдущую
  работоспособную копию, а не оставлять смешанный набор библиотек.
- Удалять только файлы своей поставки. Не удалять PREFIX целиком, чужие
  launcher'ы, конфиги, логи, кэш или состояние восстановления.
- Установка с DESTDIR только собирает файлы: не запускает программу, не
  создаёт пользовательский конфиг и не вызывает sudo/сетевые команды.

**Готово, когда:** установка работает без root в отдельный prefix, повторная
установка корректна, удаление сохраняет пользовательские и посторонние файлы,
ошибка копирования не повреждает предыдущую установку.

## 4. Добавить config init

- `amnezia-proxy-manager config init` создаёт шаблон в выбранном месте:
  `--config`, AMNEZIA_PROXY_CONFIG, XDG-путь; выбранный legacy-конфиг
  считается уже существующим и не перезаписывается.
- Новый приватный каталог создаётся с правами 700, файл — сразу с 600.
  Существующие каталоги проверяются без изменения прав чужих родителей.
- Существующий файл, включая dangling symlink, не перезаписывается;
  симлинки в родительском пути отклоняются. Создание защищается от гонки
  между проверкой наличия и записью файла.
- Вывести путь и следующие шаги: заполнить параметры, выполнить
  `config validate`, затем `doctor` и `start`. Значения секретов не выводить.
- Создание шаблона не требует sudo и не создаёт runtime/state/cache.
  Незаполненный шаблон остаётся невалидным до ввода пользовательских данных.

**Готово, когда:** проверены XDG/custom/legacy-сценарии, права 700/600,
повторный вызов, симлинки и конкурирующее создание файла. Существующий
пользовательский конфиг остаётся побайтно неизменным.

## 5. Добавить doctor для подготовки окружения

- Команда работает до настройки конфига, без sudo, сетевых запросов и записи
  файлов. Проверяет Linux, версию Bash и наличие базовых внешних команд.
  Проверку версии Bash разместить до использования несовместимого синтаксиса.
- Разделить базовые зависимости и зависимости `run`: bwrap, setpriv и другие
  требуемые sandbox-команды проверяются через `doctor --sandbox`.
- При доступном корректном конфиге учитывать условные зависимости, например
  resolvconf при заданном DNS. Невозможность проверить условие обозначать явно.
- Перечислить недостающие компоненты и их назначение за один вызов.
  Не устанавливать пакеты и не объявлять проверку наличия команды доказательством
  рабочего AWG kernel module, user namespaces или VPN-соединения.
- Существующий `diagnose` оставить проверкой работающего стека. Зафиксировать
  exit codes doctor: 0 — проверенные требования выполнены; 1 — найдена проблема;
  2 — неверные аргументы. Непроверенные условия указывать в выводе.

**Готово, когда:** тесты с ограниченным PATH показывают все отсутствующие
зависимости, обычный doctor не требует bwrap, `--sandbox` его требует;
команда не меняет сеть и файловую систему.

## 6. Определить безопасное обновление и удаление

- Для первой поставки обновление/удаление требуют остановить `start` и все
  активные `run` прежней установленной версией. Это особенно важно для
  forwarder: абсолютный путь входит в проверку принадлежности процесса.
- Незавершённая очистка после аварии также требует `stop` старой версией.
  Runtime-файлы с ownership-записями не удаляются установщиком.
- Для текущего пользователя добавить preflight-проверку активного процесса
  и оставшегося состояния по выбранным XDG/AMNEZIA_PROXY_* путям. При обнаружении
  состояния выводить команду восстановления и прекращать замену/удаление.
- Для системной установки документировать остановку всех использующих её
  пользователей и custom-конфигов. Проверка одного пользовательского runtime
  не доказывает отсутствие чужих запущенных экземпляров.
- Откат — повторная установка прежнего релизного архива после остановки стека.
  Сохранять доступ к прежней версии до успешного завершения замены.

**Готово, когда:** сценарий install → start → stop → update → start проходит;
при активном или незавершённом пользовательском состоянии update/uninstall
отказывают до изменения файлов; проверен возврат к предыдущему релизу.

## 7. Проверить поставку в CI

- Добавить `tests/install.sh` для пользовательского и DESTDIR-prefix,
  повторной установки, удаления, отказов и путей с пробелами.
- Запускать установленную копию из постороннего каталога с недоступным
  checkout. Проверить Python-helper'ы, CLI-конфиг и GUI launcher.
- Проверять `config init` и doctor без сетевых прав; выполнять sandbox-тесты
  для установленной копии. Настоящие bwrap-монтирования требуют отдельной
  среды с user namespaces: текущий Docker их не подтверждает.
- Расширить изолированный Docker-прогон kernel-тестами установленной копии.
  Добавить lifecycle-проверки остановки forwarder и восстановления состояния.
- Сохранить весь текущий тестовый набор, ShellCheck, actionlint и diff-check.

**Готово, когда:** CI проверяет checkout и установленную копию, полный
Docker-набор проходит; реальные bwrap-проверки выполнены в подходящей среде.
Ручной запуск установленной версии с настоящими AWG/3proxy и GUI подтверждён
отдельно — mock/kernel-тесты его не заменяют.

## 8. Подготовить первый релиз

- В README основным сценарием сделать установку, настройку и команды из PATH;
  инструкции запуска из checkout оставить в разделе разработки.
- Описать PATH для `~/.local/bin`, зависимости, обновление, откат, удаление,
  восстановление после аварии и границу между doctor и diagnose.
- Добавить сборку архива с явным списком файлов и SHA256; версия CLI и
  версия архива должны совпадать. Установленные файлы не требуют Git.
- Проверить архив на чистом Linux-окружении по опубликованной инструкции.
  Выпуск тега и публикация артефактов выполняются отдельным действием.

**Готово, когда:** пользователь проходит путь архив → install → config init →
настройка → config validate → doctor → start → GUI → stop → uninstall;
конфиг и логи сохраняются после удаления программы.

## Порядок реализации

Шаги 1–3 — первый коммит с работающей установкой и базовыми install-тестами.
Шаги 4–5 — отдельные коммиты с командами настройки и диагностики.
Шаги 6–7 — завершение правил обновления и полного набора проверок;
защита установки от активного состояния должна быть готова до первого релиза.
Шаг 8 — документация и подготовка релизного архива.

Проверки добавляются вместе с соответствующей реализацией; шаг 7 объединяет
их в проверку всей установленной поставки.
