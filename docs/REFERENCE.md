# Технический справочник

Основное описание и быстрый старт — в [README](../README.md).
Все ключи и переменные окружения описаны в [справочнике конфигурации](CONFIGURATION.md).
Здесь собраны подробности диагностики, сетевой защиты и разработки.

## Зависимости

Для установки нужны `make` и `python3`; инструкция — [INSTALLATION.md](INSTALLATION.md).

Linux с `/proc`, Bash 4.1+, AmneziaWG (`awg`, `awg-quick`), `3proxy`,
`curl`, `ip`/`ss` (iproute2), `nft` (nftables), `flock` (util-linux),
`timeout` (coreutils), `sudo`, `python3`. При настроенном DNS нужен `resolvconf`.
Для sandbox дополнительно нужны `bwrap` и `setpriv`. Фактические требования
зависят от включённых компонентов и BLOCK_IPV6: proxy-only с блокировкой
IPv6 off не требует AWG, nftables и sudo для обычного start.

## Конфигурация

### Проверка конфигурации

`config validate` не создаёт каталогов, не пишет лог, не вызывает sudo и не
обращается к DNS. Ошибки содержат имя параметра/номер строки, но не его секретное
значение. Шаблон `config.example` не проходит проверку до замены `replace-me`
на настоящие ключи. Ключи должны быть Base64 для 32 байт; `PRESHARED_KEY` можно
оставить пустым, если он не используется на сервере.

Проверяются неизвестные и повторяющиеся параметры, порты 1–65535 и различие
локальных портов, имя интерфейса, IPv4 CIDR в `ADDRESS`, hostname/IPv4 endpoint
с портом, HTTPS URL, MTU, keepalive, J/S, диапазоны H1–H4 и `BLOCK_IPV6=on/off`.
Числа задаются в десятичном виде без ведущих нулей. `Jmin <= Jmax`, диапазоны
H1–H4 не должны пересекаться. `DNS` пока принимает только IPv4, upstream —
IPv4 или hostname. Значения I1–I5 остаются строками: их семантику проверяет
установленная версия AWG. Сетевую доступность и совместимость AWG эта команда
не подтверждает.

### Ссылка vpn://

Параметр `VPN_LINK` принимает ссылку `vpn://`, которую выдают клиент Amnezia или
серверные панели (экспорт «Оригинальный формат Amnezia WG»). Если ссылка не
пуста, туннель настраивается из неё: `PRIVATE_KEY`, `PUBLIC_KEY`,
`PRESHARED_KEY`, `ADDRESS`, `ENDPOINT` и параметры обфускации
`Jc`/`Jmin`/`Jmax`/`S1`–`S4`/`H1`–`H4`/`I1`–`I5`. Ручные значения этих полей
при заданном `VPN_LINK` игнорируются, а `WG_INTERFACE`, прокси и настройки
песочницы остаются в силе. Пропущенные в ссылке параметры получают обычные
defaults.

Из ссылки намеренно не берутся `DNS`, `WG_MTU`, `PERSISTENTKEEPALIVE` и
маршрутизация (`ALLOWED_IPS`, `IPLIST_URLS`). `DNS` по-прежнему управляется
параметром `DNS` (пустой — системный DNS), `WG_MTU` — параметром `WG_MTU`
(`auto` по умолчанию), keepalive — параметром `PERSISTENTKEEPALIVE` (25).
Список `allowed_ips` внутри `vpn://` описывает намерения сервера (обычно
`0.0.0.0/0`) и не перекрывает пользовательский сплит-туннель: маршруты
настраиваются через `ALLOWED_IPS`/`IPLIST_URLS`, при обоих пустых действует
`0.0.0.0/0`.

Ссылка декодируется локально без обращения к сети: payload — base64url от JSON
либо от `4 байта big-endian длины + zlib(JSON)` (формат `amneziawg-installer`).
Из JSON берётся контейнер `amnezia-awg` и его `last_config`/нативный `.conf`.
`DNS` берётся из верхнеуровневых `dns1`/`dns2`, а не из нативного конфига, где
могут стоять плейсхолдеры `$PRIMARY_DNS`. Для декодирования нужен `python3`.
Ссылка не выводится в логи и не передаётся в argv процесса.

Формат строк: `KEY=value`, при необходимости с парой внешних кавычек.
Комментарии располагаются на отдельных строках. Shell-подстановки и escape
последовательности не выполняются. Пустые числовые значения считаются ошибкой;
отсутствующие необязательные параметры получают defaults. При повторной
загрузке значения из предыдущего конфига или одноимённых env-переменных не
наследуются. Пароль, имя пользователя и путь лога экранируются при генерации
конфига 3proxy.

### Остановка и коды диагностики

`stop` использует сохранённое runtime-состояние и работает даже при удалённом
или испорченном исходном конфиге. Повторный `stop` после успешной очистки
завершается успешно. Во время запуска можно отправить остановку менеджеру,
не ожидая освобождения startup-lock. Ожидание менеджера ограничено примерно
60 секундами, 3proxy — 3 секундами. Процесс-зомби считается завершённым;
чужой процесс при повторном использовании PID не завершается.

Привилегированные операции очистки не запрашивают пароль: используются
`sudo -n` и таймаут 10 секунд с принудительным завершением команды через ещё
2 секунды. Если credentials истекли, выполните `sudo -v`, затем повторите
`stop`. При ошибке состояние и защита сохраняются. DNS очищается повторно,
если интерфейс уже исчез; обнаруженные оставшиеся таблицы awg-quick требуют
ручной проверки и не маскируются сообщением об успешной остановке.

`status` и `diagnose` проверяют активные порты и upstream из runtime-конфига,
принадлежность интерфейса и обоих loopback-listeners, фактический endpoint из
`awg show`, маршрут, содержимое правил IPv4/IPv6 firewall и HTTP/SOCKS. Новое DNS-разрешение
endpoint при этом не выполняется. Handshake проверяется после запросов;
возраст более 180 секунд считается неисправностью. Без необходимых инструментов
или sudo-доступа соответствующая проверка выводит `UNKNOWN`, а не `OK`.

| Код | Значение для `status` / `diagnose` |
|---|---|
| 0 | Все обязательные проверки прошли |
| 1 | Найдена неисправность, даже если часть проверок недоступна |
| 2 | Проверка неполная либо отсутствует/некорректен конфиг |
| 3 | Система остановлена, записей активных ресурсов нет |

`test` проверяет только доступность upstream: сам по себе успешный результат
не подтверждает прохождение через VPN. `config validate` возвращает 0 при
корректном конфиге и ненулевой код при ошибке.

## Каталоги

По умолчанию используются стандартные пользовательские пути:

| Назначение | Путь |
|---|---|
| Конфиг | `${XDG_CONFIG_HOME:-~/.config}/amnezia-proxy-manager/config` |
| Кэш AllowedIPs | `${XDG_CACHE_HOME:-~/.cache}/amnezia-proxy-manager/` |
| Логи | `${XDG_STATE_HOME:-~/.local/state}/amnezia-proxy-manager/` |
| PID и временные конфиги | `${XDG_RUNTIME_DIR}/amnezia-proxy-manager/` |

Если `XDG_RUNTIME_DIR` отсутствует, runtime-каталог создаётся в
`${TMPDIR:-/tmp}/amnezia-proxy-manager-$UID`.

Все пути можно переопределить:

```text
AMNEZIA_PROXY_CONFIG
AMNEZIA_PROXY_STATE_DIR
AMNEZIA_PROXY_CACHE_DIR
AMNEZIA_PROXY_RUNTIME_DIR
```

Пути должны быть абсолютными, без симлинков и компонентов `..`. Менеджер
проверяет владельцев и права всех родительских каталогов. Общий каталог вроде
`/tmp` допускается только с системным владельцем и sticky bit. Каталоги
приложения должны принадлежать текущему пользователю; доступ на запись группе
или остальным пользователям запрещён. Уже существующие симлинки, hard links
и специальные файлы внутри каталогов приложения приводят к отказу запуска.

### Защита соединения и принадлежность ресурсов

До запуска 3proxy менеджер атомарно создаёт собственную таблицу nftables.
Она блокирует TCP-соединения текущего UID к закреплённому IPv4 и порту upstream,
если выходной интерфейс не совпадает с системным индексом созданного VPN.
Обычные соединения этого же пользователя к тому же upstream тоже подпадают
под правило. Остальные адреса и порты оно не затрагивает.

Защита действует при исчезновении маршрута, удалении VPN и создании нового
интерфейса с тем же именем. Она сохраняется при аварийном завершении менеджера.
SOCKS разрешает только TCP CONNECT: UDP ASSOCIATE и BIND в этой HTTP CONNECT
цепочке не поддерживаются и отклоняются явно.

При остановке сначала подтверждается завершение 3proxy, затем удаляется
принадлежащий запуску туннель и только после этого снимается защита. Ошибка
оставляет состояние для повторного `stop`. Firewall хоста целиком никогда
не очищается. Ручное удаление таблицы nftables администратором снимает защиту.

Существующий интерфейс менеджер не захватывает. Для удаления проверяются
сохранённые имя, системный индекс и идентификатор загрузки ОС. PID процессов
проверяется вместе со временем создания и идентификатором загрузки. Изменение
`WG_INTERFACE` в конфиге не меняет цель очистки уже запущенного туннеля.

Перед переходом со старой версии остановите её прежним скриптом или Ctrl+C:
старые PID-файлы без идентификатора процесса новая версия не принимает как
разрешение на завершение живого процесса. После аварии выполните `stop` перед
новым `start`. Не удаляйте runtime-каталог до очистки ресурсов. При потере
записи принадлежности или несовпадении интерфейса потребуется ручная проверка;
менеджер откажется удалять неподтверждённый ресурс.

### IPv4-only и блокировка IPv6

По умолчанию `BLOCK_IPV6=on`: до DNS-разрешения, загрузки IP-списков и запуска
туннеля атомарно устанавливается отдельная таблица nftables семейства `ip6`.
Она отклоняет исходящий IPv6 **всех локальных процессов**, кроме трафика через
loopback (`::1` продолжает работать). Это касается и приложений, не использующих
прокси. Ошибка установки запрещает запуск независимо от режима healthcheck.
Системные sysctl IPv6 не меняются.

Блокировка снимается последней при успешной остановке. При ошибке очистки или
`SIGKILL` она остаётся; выполните `stop` (при необходимости сначала `sudo -v`).
Удаляется только таблица, записанная в runtime `ipv6.owner`; чужие правила не
очищаются. Не удаляйте runtime-состояние вручную до остановки.

`BLOCK_IPV6=off` явно отключает эту защиту и выдаёт предупреждение. Без активного
правила диагностика считает защиту неполной (код 2, если нет других ошибок).
Опция не включает поддержку IPv6 в `ADDRESS`, endpoint или upstream-прокси:
они должны иметь IPv4. AAAA-only endpoint/upstream приводит к отказу запуска.
Если системный DNS доступен исключительно по IPv6, разрешение имён после
блокировки также не сработает; запуск завершится с очисткой.

Это защита локального OUTPUT, не FORWARD: транзитный трафик и отдельные сетевые
пространства контейнеров ею не защищены. Прямой IPv4 вне выборочных маршрутов
тоже не блокируется — менеджер не является полным VPN kill switch для хоста.
Диагностика проверяет содержимое правила: один неудачный `curl -6` не доказывает
блокировку, поскольку причиной может быть отсутствие IPv6-связности.

## VPN и proxy transport

### Маршруты VPN

`ALLOWED_IPS` задаёт адреса и подсети вручную, а `IPLIST_URLS` загружает их через
HTTPS. Если задан хотя бы один источник, используется объединение списков:

```text
ALLOWED_IPS="192.0.2.7, 198.51.100.0/24"
IPLIST_URLS="https://lists.example.org/ipv4.txt"
```

Адрес без маски означает `/32`; разделители — пробелы или запятые. В ответе
HTTP также допустимы переносы строк и комментарии после `#`. Невалидные ручные
записи отклоняет `config validate`. В загруженном списке невалидные записи
отбрасываются с предупреждением; ошибка любого запроса или отсутствие валидных
адресов запрещает запуск. Ошибка запроса не включает полный VPN и не заменяет
последний сохранённый список. Автоматического fallback на кэш пока нет.

После добавления upstream и DNS Python 3 (`ipaddress.collapse_addresses`)
нормализует CIDR, удаляет покрытые записи и объединяет соседние блоки в
минимальный набор с тем же множеством IPv4-адресов. Оптимизированный список
попадает в кэш и конфиг AWG; лог показывает число префиксов до и после обработки.
Ошибка обработки запрещает запуск и сохраняет прежний кэш. Агрегация может
уменьшить специфичность маршрутов: более специфичные маршруты других интерфейсов
будут иметь приоритет по обычным правилам маршрутизации Linux.

Если оба параметра пусты или отсутствуют, используется `AllowedIPs = 0.0.0.0/0`:

```text
ALLOWED_IPS=""
IPLIST_URLS=""
```

Это новый default: ранее пустой `IPLIST_URLS` отправлял в VPN только прокси.
Теперь через VPN идёт IPv4-трафик хоста, для которого нет более специфичного
системного маршрута (например, маршрут локальной сети сохраняется).
`awg-quick` использует policy routing и fwmark для соединения с VPN-сервером;
проверка endpoint и оценка MTU учитывают эту метку. IPv6 по-прежнему блокируется
при `BLOCK_IPV6=on`. Доступность сетей за сервером зависит от его маршрутов,
forwarding/firewall и NAT; клиентский список сам по себе не открывает доступ.

В выборочном режиме upstream-прокси и настроенный DNS автоматически добавляются
как служебные `/32`. Чтобы сохранить прежний режим «только прокси», укажите его
IPv4 в `ALLOWED_IPS` и оставьте `IPLIST_URLS` пустым. Списки определяют маршруты,
а не ACL: остальные IPv4-адреса продолжают использовать системную сеть.
Изменения конфигурации применяются после `restart`.

Перед поднятием туннеля hostname upstream-прокси преобразуется в IPv4. Все
полученные адреса добавляются в `AllowedIPs`, а выбранный адрес фиксируется в
конфиге 3proxy до следующего рестарта. Благодаря этому DNS-ответ 3proxy не может
случайно указать на адрес, который не маршрутизируется через AmneziaWG.

AWG endpoint также разрешается в IPv4 перед стартом: первый полученный A-адрес
фиксируется в WG-конфиге до рестарта. Проверка маршрута использует этот же адрес;
`awg-quick` не выбирает AAAA повторным DNS-разрешением. Без IPv4 запуск запрещён.

После запуска проверяются два обязательных инварианта:

- маршрут к endpoint не должен проходить через создаваемый AWG-интерфейс;
- маршрут к фактическому upstream-прокси обязан проходить через него.

До запуска 3proxy проверяется занятость локальных портов, а после запуска —
наличие обоих listening sockets. Одного существующего PID недостаточно для
статуса «готово».

Нарушение любого из условий считается ошибкой запуска и вызывает cleanup.

HTTP-вход 3proxy использует parent типа `http`, а SOCKS-вход — parent типа
`connect+` вместе с `fakeresolve`. Это преобразует SOCKS в upstream HTTP
CONNECT и оставляет разрешение целевого hostname upstream-прокси, как ожидает
клиент `socks5h`. Проверка `diagnose` отдельно тестирует оба локальных протокола.

### MTU

Рекомендуемый режим для новых конфигов:

```text
WG_MTU=auto
```

В этом режиме строка `MTU` не записывается во временный AWG-конфиг и
`awg-quick` самостоятельно выбирает MTU маршрута к endpoint минус 80 байт.
Фиксированное рабочее значение можно оставить без изменений, например
`WG_MTU=1390`.

Команда `diagnose` показывает настроенное значение, оценку `awg-quick` и
фактический MTU поднятого интерфейса. Значение `PROXY_MAXSEG` предназначено
только для редких проблем PMTUD, требует 3proxy 0.9.6+ и обычно не нужно при
правильном `WG_MTU`.

### DNS и стартовая проверка

Пустой `DNS` сохраняет системное разрешение имён. Если указан IPv4 DNS,
`awg-quick` временно подключает его через `resolvconf`, а менеджер автоматически
добавляет адрес DNS в `AllowedIPs`, чтобы запросы не ушли мимо туннеля.

После запуска HTTP и SOCKS проверяются через `HEALTHCHECK_URL`. Поведение
настраивается параметром `STARTUP_HEALTHCHECK`:

- `off` — не проверять;
- `warn` — оставить систему запущенной и вывести предупреждение;
- `strict` — считать неуспешную проверку ошибкой и откатить запуск.

Проверки игнорируют `NO_PROXY`/`no_proxy` и `.curlrc`, требуют HTTP 2xx и не
переходят по редиректам. Ответы 3xx/4xx/5xx и ошибки соединения не считаются
работоспособной цепочкой. MTU-оценка не заменяет измерения PMTU или больших
передач данных.

Для подробной проверки выполните:

```bash
./apm diagnose
```

Поведение основано на штатном расчёте MTU в
[AmneziaWG `awg-quick`](https://github.com/amnezia-vpn/amneziawg-tools/blob/master/src/wg-quick/linux.bash)
и официальной документации
[3proxy parent/DNS/MSS](https://github.com/3proxy/3proxy/wiki/3proxy.cfg).

## Песочница для AI-агентов

`run` запускает команду в изолированном network namespace, чтобы агент (Claude Code,
Codex и т.п.) физически не мог видеть сетевую топологию хоста. Требуется уже
запущенный `start`: туннель, 3proxy и guard должны работать.

```bash
./apm start
./apm run -- codex --version
./apm run -- bash -c 'ip link; ip route; curl -x http://10.200.0.1:8081 https://api.ipify.org'
```

Sandbox явно восстанавливает пользовательские `PATH` и `HOME` после `sudo`,
а `USER` и `LOGNAME` берёт из UID запускающего пользователя. Поэтому команды
из `~/.local/bin` и пользовательских установок Node.js можно запускать по имени,
если они доступны в исходном `PATH` и их файлы не скрыты внутри sandbox.

Цепочка трафика агента:

```text
агент → 10.200.0.1 (veth) → forwarder → host 3proxy → VPN → upstream
```

Внутри namespace видны только `lo` и veth-пара; единственный маршрут ведёт к
host-стороне veth (`10.200.0.1/32` по умолчанию), default-route отсутствует;
назначение адреса /30 также создаёт connected route. Это пока не запрещает
доступ к другим сервисам на host-адресе veth: отдельный INPUT/FORWARD guard
планируется отдельно.
Forwarder (`lib/sandbox_forwarder.py`, raw TCP relay) слушает на host-стороне veth
и проксирует на loopback-порты 3proxy. Агент использует прокси по адресу
`10.200.0.1:$LOCAL_HTTP_PORT` / `socks5h://10.200.0.1:$LOCAL_SOCKS_PORT` (переменные
`HTTP_PROXY`/`ALL_PROXY` выставляются автоматически).

Filesystem изолируется через `bwrap`: `/usr /bin /sbin /lib /lib64 /etc /opt`
подключаются read-only, `$HOME` и рабочий каталог — read-write, `/run /var /root`
и прочие каталоги хоста отсутствуют, а host-`/proc` заменяется свежим procfs.
Секретные пути скрываются всегда: сам конфиг, `~/.ssh`,
`~/.aws`, `~/.gnupg`, `~/.config/gcloud`, `~/.azure`, `~/.kube`; дополнительные —
через `SANDBOX_HIDE_PATHS`. Агент работает от вашего UID без sudo и capabilities.

Параметры: `SANDBOX_NETNS_NAME` (имя namespace), `SANDBOX_VETH_SUBNET` (пара /30),
`SANDBOX_HIDE_PATHS` (дополнительные скрытые пути), `SANDBOX_NO_PROXY`
(исключения `NO_PROXY` через запятую), `SANDBOX_EXPECTED_EXIT_IP` (fail-closed
сверка выходного IP). Настройка netns требует `sudo` (интерактивно, как `start`);
очистка — `sudo -n` как у остального `stop`. Агенту всегда выставляется
`NODE_OPTIONS=--dns-result-order=ipv4first`.

Одновременно допускается только один `run`: отдельный flock удерживается до
завершения сессии. `stop` отказывает при активной сессии до остановки 3proxy;
сначала завершите `run`. Veth получают случайные имена; namespace остаётся
заданным через `SANDBOX_NETNS_NAME`. Запись владения содержит inode namespace
и ifindex обоих veth, а forwarder — PID + boot ID/starttime. Оба listener-порта
должны успешно bind до READY; из namespace проверяются HTTP и SOCKS.

Cleanup при EXIT/INT/TERM не запрашивает пароль. При истёкших sudo credentials,
занятом namespace или ошибке удаления состояние сохраняется для повторного
`stop`. Crash между созданием ресурса и записью его идентичности оставляет
`pending`: автоматическая очистка такого существующего ресурса запрещена.
Перед обновлением с прежнего формата завершите старый `run`/`stop` старой версией;
legacy owner/PID без идентичности новая версия автоматически не удаляет и не
сигналит. Не стирайте owner вручную, не проверив остаточные ресурсы.

`SANDBOX_NO_PROXY` по умолчанию пуст — весь трафик идёт через VPN-прокси. Учтите:
localhost-сервисы хоста (например MCP) из netns недоступны в любом случае, потому
что у агента отдельный loopback; однако wildcard listeners могут быть доступны
через адрес host veth, пока отдельный guard не реализован. `NO_PROXY` не выдаёт
сетевого разрешения и не отменяет изоляцию netns.

Запросы агента видны в `amnezia-proxy-manager logs`: forwarder пишет в
`${STATE_DIR}/sandbox.log` по строке на соединение — метод HTTP и проверенный
адрес для CONNECT (`CONNECT api.anthropic.com:443`), либо пометку `socks` для
SOCKS-входа, с адресом veth и портом слушателя. Так изолированный трафик
отличим от прямых обращений к 3proxy хоста.
Неизвестные/неполные первые TCP-пакеты обозначаются `tcp`. URL path/query,
userinfo, заголовки и содержимое не записываются; TLS не расшифровывается.
Ошибка записи лога выдаёт предупреждение, но не обрывает соединение.

### Режим GUI (`run --gui`)

`run --gui -- <команда>` запускает GUI-приложение (например ChatGPT Desktop) в том
же изолированном netns, но дополнительно пробрасывает внутрь bwrap дисплей и сессию:
`$XDG_RUNTIME_DIR` (Wayland/dbus/pipewire) и `/tmp/.X11-unix` монтируются read-write,
`/dev/shm` — для Chromium, а `/dev/dri` и `/dev/nvidia*` — через `--dev-bind` (GPU).
Переменные `DISPLAY`, `WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`,
`XAUTHORITY` и `XDG_SESSION_TYPE` пробрасываются явно (`sudo` их ресетит). В отличие от
обычного `run`, supplementary-группы пользователя сохраняются (`render`/`video` для GPU).
Файл `XAUTHORITY` монтируется отдельно read-only, в том числе из `/tmp`.
Runtime-каталог самого менеджера скрыт: сгенерированные AWG/3proxy-конфиги с
ключами и паролем upstream недоступны GUI-приложению.

```bash
./apm start
./apm run --gui -- chatgpt \
    --no-sandbox --proxy-server=http://10.200.0.1:8081 \
    --disable-quic --force-webrtc-ip-handling-policy=disable_non_proxied_udp
```

Для Chromium/Electron эти флаги автоматически добавляет launcher:

```bash
./apm-gui -- chatgpt
```

Он поддерживает `--config ПУТЬ` и получает адрес из `HTTP_PROXY` уже внутри
sandbox, поэтому использует активный порт 3proxy даже после изменения конфига
без рестарта стека. Выбор конфига остаётся за основным менеджером.

Адрес прокси внутри sandbox — host-сторона veth (`10.200.0.1` по умолчанию, т.е.
base+1 из `SANDBOX_VETH_SUBNET`). Electron не надёжно читает proxy-env, поэтому
`--proxy-server` обязателен; `--no-sandbox` обязателен, потому что собственный
sandbox Chromium не работает внутри bwrap с `--cap-drop ALL` — сетевым рубежом
остаётся netns (без default-route), файловым — bwrap.

Ослабление безопасности: GUI-режим монтирует `$XDG_RUNTIME_DIR` read-write и сохраняет
supplementary-группы, поэтому приложению видны сессионные сокеты (rootless
`docker.sock`, ssh/gpg-agent). Это приемлемо для интерактивного GUI-приложения
пользователя, но не для недоверенных CLI-агентов — флаг опциональный и в обычный
`run` не включается.

Ограничение: это изоляция процесса от сетевой топологии и секретных файлов, а не
полный kill-switch хоста. Секреты, переданные агенту в переменных окружения
(например `ANTHROPIC_API_KEY`), не скрываются — это креды самого агента.

## Разработка

Проверки не поднимают туннель и не требуют сетевого доступа:

```bash
for file in amnezia-proxy-manager bin/amnezia-proxy lib/*.sh tests/*.sh; do
    bash -n "$file" || exit
done
bash tests/run.sh
bash tests/security.sh
bash tests/behavior.sh
bash tests/ipv6.sh
bash tests/routes.sh
python3 tests/route-collapse.py
```

Полный набор проверок в Docker, включая реальные правила nftables:

```bash
bash tests/docker.sh
```

Первая сборка скачивает Debian и тестовые зависимости. Сам тестовый контейнер
запускается с `--network none`, read-only файловой системой, временным `/tmp`
и единственной добавленной capability `NET_ADMIN`. Нет `--privileged`,
host network, Docker socket или каталогов хоста внутри контейнера. Build
context ограничен кодом, тестами и `config.example`; личные конфиги не копируются.

Проверяется разрешённый выход через dummy VPN, блокировка альтернативного
маршрута, блокировка нового интерфейса с тем же именем и обнаружение пустого
firewall. Дополнительно запускаются реальные curl-запросы к локальным TLS/HTTP/
SOCKS-серверам и проверки TERM, процесса, игнорирующего TERM, и зомби.
Полный VPN проверяется на policy routing: обычные пакеты используют туннель,
endpoint с fwmark использует внешнюю сеть, а реальная петля отклоняется.
IPv6 включается sysctl только внутри сетевого пространства контейнера:
проверяются отправка до блокировки, реальный REJECT после неё, работа `::1`,
восстановление после остановки и `SIGKILL`, сохранность чужих правил и opt-out.
Контейнер удаляется
после теста, образ остаётся для следующих запусков. Это проверка сетевой защиты
на реальном ядре, но не end-to-end тест настоящего AmneziaWG и upstream-прокси.
Вне Docker аналогичный сетевой тест: `bash tests/netns.sh` (нужны разрешённые
user/network namespaces).



## Независимые компоненты

VPN_ON и PROXY_ON по умолчанию true; принимаются true/false, on/off, 1/0.
В VPN-only обязательны только VPN-параметры, в proxy-only — только proxy-параметры.
VPN_LINK при отключённом VPN не декодируется. Синтаксис и неизвестные ключи
проверяются всегда. Отключённые секции не получают проверки их семантики.
BLOCK_IPV6 сохраняет самостоятельную политику, default on.

Runtime session.state содержит версию, ID, фазу и не секретные параметры режима.
Он читается как данные, не исполняется. status/diagnose/run используют его даже
при отсутствующем пользовательском конфиге; stop восстанавливается по ownership.
Старое runtime-состояние следует очистить прежней версией перед обновлением.
Остатки ресурсов блокируют новый запуск. Изменение конфига применяется restart;
невалидный новый конфиг проверяется до остановки прежней сессии.

В proxy-only transport guard не устанавливается; используется системный маршрут,
включая внешний VPN, если его настроил пользователь. В combined guard обязателен.
В VPN-only proxy test неприменим (код 2), run отказывает без создания namespace.
VPN-only сохраняет существующее ограничение: полного IPv4 kill switch хоста нет.
BLOCK_IPV6=off по-прежнему даёт код диагностики 2 как неполную защиту.

### Ожидание VPN-соединения

`VPN_CONNECT_TIMEOUT=30` (целое 1–300 секунд) ограничивает ожидание свежего
handshake выбранного peer. Проверка обязательна при VPN_ON=true, включая
VPN-only, и не зависит от STARTUP_HEALTHCHECK или публичного HTTP-сервиса.
Интерфейс UP сам по себе не считается подтверждением соединения.

Для активного запроса handshake keepalive временно переключается 0 → 1 секунду,
затем восстанавливается PERSISTENTKEEPALIVE, в том числе при неуспехе. Это
использует механизм отправки keepalive при включении интервала в
[AmneziaWG](https://github.com/amnezia-vpn/amneziawg-linux-kernel-module/blob/master/src/netlink.c).
Сам конфиг пользователя и сгенерированный AWG-конфиг не переписываются.
Если проверка недоступна или handshake не получен, запуск прекращается до
ready/старта proxy; cleanup удаляет ресурсы попытки. Восстановление keepalive
и очистка могут занять дополнительное время после таймаута ожидания.
Успешный handshake не гарантирует доступность внешних сайтов или DNS.

### Недоступные привилегированные проверки

Если status/diagnose показывают Firewall/IPv6/Endpoint/Handshake UNKNOWN,
выполните `sudo -v` в том же терминале и повторите команду. Проверки работают
через неблокирующий sudo; UNKNOWN означает невозможность подтвердить состояние,
а не автоматически отсутствие или исправность правил. Не запускайте весь
менеджер через sudo: конфиг, runtime и UID должны оставаться пользовательскими.

run (включая GUI launcher) запрашивает sudo-авторизацию до блокировок и создания
ресурсов. Для совместной сессии guard проверяется по активным upstream-IP/порту
из runtime-конфига 3proxy. Отсутствие/несоответствие правила и недоступность его
проверки дают разные сообщения; оба случая запрещают запуск sandbox.
Оценка MTU без доступного фактического endpoint отмечается UNKNOWN, остальные
проверки диагностики продолжаются.

## Проверка окружения перед запуском

`doctor` проверяет Linux, Bash 4.1+ и наличие внешних команд. При корректном
конфиге учитывает VPN_ON, PROXY_ON, BLOCK_IPV6 и DNS; при отсутствующем конфиге
проверяет default VPN+proxy и сообщает, что DNS-условия не определены. Невалидный
конфиг даёт ошибку и проверку зависимостей обоих компонентов.

`doctor --sandbox` дополнительно требует bwrap/setpriv, ip/sudo/python3/curl
и включённый proxy. Код 0 означает, что проверенные требования выполнены,
1 — найдены проблемы, 2 — неверные аргументы команды.

doctor не вызывает sudo, не делает сетевых запросов и не пишет файлы. Наличие
команд не доказывает поддержку AWG kernel module, user namespaces, sudo-права
или доступность сервера. `diagnose` проверяет уже запущенную сессию.
