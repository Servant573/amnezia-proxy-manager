## 2. Корректность кода

### 1. [P1] GUI открывает сгенерированные конфиги с секретами — blocking

**Место:** `lib/sandbox.sh:308`.

При стандартном размещении runtime в `$XDG_RUNTIME_DIR/amnezia-proxy-manager` новый bind всего `$XDG_RUNTIME_DIR` открывает приложению `3proxy.cfg` с логином/паролем upstream и `${WG_INTERFACE}.conf` с `PrivateKey`/`PresharedKey`. Они существуют всё время работы стека; права 0600 не помогают, поскольку приложение запускается с тем же UID. Последующее маскирование скрывает только исходный `CONFIG_FILE`, legacy-конфиг и перечисленные секретные пути, но не runtime-копии. Это отдельная утечка файловых секретов сверх документированного доступа к сессионным сокетам.

**Проверка:** настоящий bwrap с синтетическими конфигами: в CLI оба generated-файла недоступны; при `SANDBOX_GUI=1` оба читаются. Сеть и sudo для воспроизведения не нужны.

**Исправление:** после монтирования GUI скрыть собственный `RUNTIME_DIR` пустым tmpfs либо монтировать только необходимые сессионные ресурсы. Проверить чтение обоих generated-конфигов в GUI и CLI. Не считать предупреждение о docker/ssh-agent заменой защите VPN-ключей.

### 2. [P2] Отсутствие XDG_SESSION_TYPE аварийно завершает GUI-запуск — important

**Место:** `lib/sandbox.sh:319–321`.

Последняя итерация `for` проверяет `XDG_SESSION_TYPE`. Если переменная отсутствует или пуста, `[[ -n ... ]] && ...` возвращает 1; цикл, а затем `sandbox_gui_bindings` наследуют этот статус. Функция вызывается обычной командой из `sandbox_build_bwrap`, поэтому `set -e` завершает менеджер до запуска приложения. `DISPLAY` и корректный X11-cookie сами по себе недостаточны: например, окружение X11/SSH может не задавать тип сессии. Опциональная переменная не должна становиться обязательной без диагностики.

**Проверка:** отдельный Bash с `source bin/amnezia-proxy`, `SANDBOX_GUI=1`, `BWRAP_ARGS=()`, `unset XDG_SESSION_TYPE`, вызов `sandbox_gui_bindings`: exit 1, следующая команда не выполняется. Новый тест всегда задаёт переменную и потому пропускает регрессию.

**Исправление:** явный `return 0` в конце helper; отдельный тест запуска в дочернем Bash с `set -e`, пустым и отсутствующим `XDG_SESSION_TYPE` (вызов в `if` подавил бы errexit и скрыл проблему).

### 3. [P2] Chromium получает порт из изменённого конфига вместо активного listener — important

**Место:** `bin/amnezia-proxy-gui:70–71`, использование в `bin/amnezia-proxy-gui:79`.

`do_run` специально читает порты из действующего `3proxy.cfg` через `read_active_proxy_ports`. Новый launcher независимо читает `LOCAL_HTTP_PORT` из пользовательского конфига и передаёт его Chromium через `--proxy-server`. Если после `start` с 8081 изменить конфиг на 8181 без рестарта, forwarder и healthcheck продолжат работать с 8081, но приложение отправит запросы на 8181 и потеряет доступ к сети. Переменные `HTTP_PROXY` внутри bwrap при этом правильные, однако обязательный Chromium-флаг их перекрывает.

**Проверка:** synthetic runtime с `proxy -p8081`, пользовательский конфиг с `LOCAL_HTTP_PORT=8181`: `read_active_proxy_ports` возвращает 8081, launcher формирует `--proxy-server=http://10.200.0.1:8181`. Команда `exec` launcher была перехвачена Bash-функцией; реальный manager/GUI/netns не запускался.

**Исправление:** формировать Chromium-флаг внутри sandbox из уже подготовленного `HTTP_PROXY`, чтобы использовать тот же адрес, что forwarder. Отказаться от второго парсера порта/подсети.

### 4. [P2] XAUTHORITY передаётся без монтирования cookie-файла — important

**Место:** `lib/sandbox.sh:319–320`.

Если `XAUTHORITY` указывает на файл вроде `/tmp/xauth-XXXXXX`, helper задаёт правильный путь в окружении, но сам файл скрыт `--tmpfs /tmp`. Проброс `/tmp/.X11-unix` даёт транспорт до X-сервера, но не доступ к cookie для авторизации. В таком X11-сеансе приложение не сможет подключиться к дисплею. Файлы в `$HOME` и в проброшенном `$XDG_RUNTIME_DIR` доступны, поэтому happy-path с `$HOME/.Xauthority` из теста не показывает дефект.

**Проверка:** создан синтетический cookie в отдельном каталоге `/tmp`; после GUI-сборки настоящий bwrap сохраняет `XAUTHORITY`, но `test -r "$XAUTHORITY"` не проходит.

**Исправление:** при заданном читаемом `XAUTHORITY` монтировать конкретный файл read-only после создания tmpfs `/tmp`; добавить проверку чтения содержимого через настоящий bwrap.
